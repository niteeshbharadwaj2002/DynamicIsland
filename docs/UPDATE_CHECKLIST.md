## 1. Strategy (decided)

**Rebuild on upstream, then record NotchIQ history with an `-s ours` merge.**
`git merge upstream/main` would leave 58 marker-conflicts inside files upstream has since split or rewritten (overlay −1231 lines, listener +1449, settings +865/+1112), so resolving markers means porting anyway, but inside one giant uncommitted merge that no executor can test incrementally.
NotchIQ's three kept areas are mostly *new* files (~90 add cleanly, no add/add) plus a bounded set of seams, so porting them onto `upstream/main` in small, compiling, tested commits is cheaper and safer.
At the end `git merge -s ours origin/main` makes `update` a descendant of both `origin/main` and `upstream/main` (push is fast-forward, PR `update → main` is clean); the `-s ours` merge drops anything not ported, so M8 has an explicit "nothing lost" audit against `origin/main`.

Ownership rule used everywhere below: **upstream owns non-UI logic** (parsers, detectors, data, services' event sources, settings keys it introduced), **NotchIQ owns the three kept areas** (Buddy, island presentation/motion/alert rules, settings app look), **hand-merge** where both matter (upstream feature rendered with NotchIQ visuals).

Working technique for every "port" item: NotchIQ delta of a file = `git diff f7d1601 origin/main -- <file>`; new NotchIQ files = `git checkout origin/main -- <paths>`; upstream version is the starting point already in the tree.
